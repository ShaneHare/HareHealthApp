D1 · Security · Invisible to user

Hash passwords in localStorage

Dev only½ day

Passwords currently live in localStorage['hh2_users'] as plaintext strings. Swap to SHA-256 + per-user salt. This is not production-grade auth (that requires a backend) but it closes the #1 App Store rejection vector and makes the on-device store safe-enough for a v1.

Before

getUsers → returns objects like { username: "ben", password: "correct-horse-battery", name: "Ben" }

After

Stored shape { username: "ben", passHash: "a3f5c…", passSalt: "f8e1…", passAlgo: "sha256-v1", name: "Ben" }

Implementation

// Drop-in replacement for login/register password handling
async function hashPassword(pw, salt) {
  const enc = new TextEncoder();
  const data = enc.encode(salt + ':' + pw);
  const buf = await crypto.subtle.digest('SHA-256', data);
  return [...new Uint8Array(buf)]
    .map(b => b.toString(16).padStart(2, '0')).join('');
}

function makeSalt() {
  const b = new Uint8Array(16);
  crypto.getRandomValues(b);
  return [...b].map(x => x.toString(16).padStart(2, '0')).join('');
}

// On register:
const salt = makeSalt();
const passHash = await hashPassword(pass, salt);
const newUser = { username, name, email, passHash, passSalt: salt, passAlgo: 'sha256-v1' };

// On login:
const computed = await hashPassword(pw, user.passSalt);
if (computed === user.passHash) { /* match */ }

Migration

On next login for a user with a legacy password field, verify the plaintext, then silently rewrite their record as hashed and delete the password field. After 30 days, reject any record still containing password — force a password reset.

Caveat: This protects against casual localStorage inspection and fixes one compliance checkbox. It does not protect against device compromise. Real auth requires a backend — that's item D3, Horizon 3.

MarketDev1 day

Why the orange banner

App Store review specifically looks for an unambiguous non-medical-device declaration inside the app, not just in App Store copy. Orange (our warn color) reads as “heads-up” without feeling dangerous like red. A dismissible banner is tempting but review rejects disclaimers that can be permanently hidden.

  • Home screen footnote — small dim line under the bottom nav on empty state.
  • Doctor Report PDF — already present, keep as-is.

Privacy Policy
Plain English Summary
Your data stays on your phone.
In 30 seconds

We don't have a server yet. Your readings, weight, blood pressure, and heart rate live only in your phone's browser storage.

We don't sell anything. No ads, no data brokers, no analytics cookies that follow you around the web.

We count events, not people. We log anonymous product metrics — “someone logged a reading” — via PostHog. No names, no readings, no identifiers leave your device.

You can clear everything. Profile → Data → Clear All Data wipes the entire record. No recovery, by design.

1. What we store
All blood pressure, heart rate, weight, BMI, and timestamp data you enter is stored in your device's localStorage under the keys hh2_readings, hh2_prefs, and hh2_users. These keys are readable only by Hare Health running on your device.
2. What we transmit
Product analytics events (see Section 6) are sent to PostHog Cloud with an anonymous device identifier. Welcome emails, if you provided one during signup, are sent via our transactional mail provider and deleted from our send log after 30 days.
3. What we do not store server-side
Health readings. Names. Email addresses (beyond send-log retention). Passwords — they are hashed on your device and never transmitted. Doctor Reports — generated and rendered on-device only.
4. Third parties
PostHog (product analytics, aggregate only). Resend or Postmark (welcome email delivery). That is the full list. We do not use Facebook, Google, Meta, TikTok, or any ad-network SDKs.

Medical Disclaimer
Read this carefully
Hare Health is not a medical device.
What that means

Hare Health is a screening and tracking tool. It helps you notice patterns in readings you already took with a real device (a clinical blood pressure cuff, a scale, a pulse oximeter).

We do not diagnose conditions. We do not replace a doctor. Our risk score is a pattern-recognition aid, not a clinical measurement.

If you're experiencing chest pain, shortness of breath, confusion, severe headache, or fainting — stop and call emergency services. Do not consult this app.

Our risk score
The Cardio Risk Index blends your recent readings against published clinical thresholds (ACC/AHA 2017 for BP, Mayo Clinic for resting HR, CDC for BMI). It is directional — it tells you whether your numbers are trending toward ranges associated with higher cardiovascular risk. It is not a diagnosis of any condition.
AI Insights
Insights are generated by language models interpreting your own data. They can be wrong. They should never override a clinical judgment, a prescribed medication regimen, or your own symptoms.
When to see a doctor
• SYS > 180 or DIA > 120 (hypertensive crisis range) — seek care today.
• Resting HR > 120 or < 40 with symptoms.
• Any reading that surprises you alongside how you feel.

M2 · Two-layer legal voice

Plain-English on top, full legal below

Market½ day drafting · 1 day legal review

Voice rules

  • Lead with one summary card in short paragraphs — the 30-second version.
  • Full legal sections below, numbered, short headers. Each section ≤ 3 sentences where possible.
  • No “heretofore,” no “the Service,” no capitalised Defined Terms. “Hare Health” is the name of the company and the app. “We” is us. “You” is you.
  • Every claim must be true. If we don't have a server, say so — don't write boilerplate about data centres we don't operate.

Terms of Service — shorter, standard. Arbitration clause optional at this stage (depends on jurisdiction — ask counsel).

D4 · Tiered input validation

Soft, warn, block.

Dev½ day

Current logger already has a clinical-threshold colouring (the .field-insight in loggerLiveUpdate()). What's missing is a hard block on physically impossible values — the thing that actually prevents bad data from contaminating the risk engine.

Three tiers

  • OK (green/neutral): value is in range. Existing clinical copy.
  • Soft warn (orange): out-of-range but clinically plausible. Save still works. Shown as an inline note.
  • Hard block (red): physically implausible — a typo. Save disabled, inline confirm prompt.

Thresholds

MetricOKWarnBlock
SYS90–14080–89, 141–180<40 or >260
DIA60–9050–59, 91–120<30 or >150
HR50–10040–49, 101–140<20 or >250
Weight (lbs)80–40060–79, 401–600<40 or >700
SYS vs DIASYS > DIA+20SYS ≤ DIA+20SYS ≤ DIA

Confirm affordance

For block-tier values, show two buttons under the input: Yes — use 135 (auto-suggest the nearest plausible value by inserting a missing digit), and Keep 35 (override — fires a validation_override event and still permits save). Overrides are valuable telemetry: they flag either genuinely unusual patients or a UX problem in the number pad.

Bucketing rules

All count properties are bucketed before send: 1, 2-3, 4-10, 11-30, 31-100, 100+. This prevents re-identification via unusual reading counts and keeps PostHog's cardinality bills sane.

Key funnels to build in PostHog

  • Activation: app_opened → register_completed → first_reading_saved → ai_insight_opened (first time).
  • Retention loop: reading_saved (day N) → reading_saved (day N+1) → reading_saved (day N+7).
  • Value-to-monetisation: first_reading_saved → pdf_exported. This is the paid-tier signal.
